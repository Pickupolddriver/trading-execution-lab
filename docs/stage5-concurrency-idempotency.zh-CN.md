# Stage 5：并发、顺序与幂等

## 当前进度：Stage 5A 已开始

第一步先在单 JVM 内把订单更新和命令重放规则讲清楚、写成可并发验证的测试。它不等同于完成整个 Stage 5：多实例协调、持久化去重以及订单簿 / 事件的原子提交仍未实现。

## 1. 订单版本与乐观更新

`Order` 为每次真实状态变更递增 `version`：确认、拒绝、唯一成交和撤单都会增加版本；重复成交不增加版本。`Order.snapshot()` 在同一把订单锁内返回版本和订单状态字段，避免调用者把不同时间点的多个 getter 拼成一份不一致快照。

处理者先读取快照版本，再提交成交：

```java
OrderSnapshot snapshot = order.snapshot();
ExecutionApplyResult result = order.applyExecution(execution, snapshot.version());
```

返回值含义：

| 结果 | 含义 | 调用者动作 |
| --- | --- | --- |
| `APPLIED` | 版本仍匹配，成交已应用 | 使用新订单状态 / 版本 |
| `VERSION_CONFLICT` | 别的更新先推进了版本；本次成交未改变状态 | 重新读取并按业务规则处理，不能盲目重放旧快照 |
| `DUPLICATE` | 相同 execution ID 和相同成交内容已应用 | 当作已完成，不重复累计 |

每个 `Order` 实例的变更方法由对象锁保护；版本检查和成交更新在同一个临界区内，所以两个线程拿着同一版本更新时，至多一个新 execution 能成功。此实现是在一个 JVM 内演示乐观版本语义，**不是**数据库或 GigaSpaces 的跨进程 compare-and-set。

相同 execution ID 如果对应不同订单、数量、价格或成交时间会抛出错误，避免把 ID 冲突静默当成正常重复。数量和价格按数值比较，`3` 与 `3.00` 视为相同值。

## 2. 命令重放

`OrderCommandProcessor.handle(...)` 在单个处理器实例中串行执行。新单使用 `(clientId, clientOrderId)` 识别请求；撤单使用 `(orderId, cancelRequestId)` 识别请求。处理器缓存第一次返回的不可变事件列表：

- 同一请求 ID、相同订单条件：重放第一次的事件，不再次撮合或撤单。
- 同一新单请求 ID、不同订单条件：返回拒绝，不覆盖原订单。
- 新单条件中的数量和价格按十进制数值规范化后比较，例如 `10.5` 与 `10.50` 相同。
- 精确撤单请求重放会返回原确认 / 拒绝，不会再次改变订单簿。

缓存查找发生在订单状态校验之前，因而即使原订单已部分成交、完成或撤销，重试原请求仍能拿到原始响应，而不是收到一个新的状态错误。

## 3. 并发基线和顺序

处理器当前用一个 `synchronized handle` 把所有命令串行化。这建立了单实例内的互斥与单一处理顺序，也保护它内部的非线程安全 `OrderBook` 和 map。但它会把不同 symbol 的命令也一起串行，且 Java monitor 不保证按 `receivedAt` 或线程启动时间 FIFO。真正需要扩展时，可以按 symbol 分配串行队列 / actor，再单独处理客户账户等跨 symbol 状态。

直接拿 `OrderBook` 实例在多个线程调用仍不安全。并发入口应经过处理器；未来把订单簿 owner 拆分时，要明确同一 symbol 的命令顺序由谁分配。

## 4. 运行与测试

```powershell
mvn -pl order-domain,exchange-simulator -am test
```

UT 覆盖：

- 两个不同成交并发使用同一个版本，只有一个更新成功，另一个收到版本冲突。
- 同一 execution 并发 / 重复重放只累计一次；同 ID 不同内容被拒绝。
- 每次有效状态变更递增版本，重复成交不递增。
- 同一新单 / 撤单请求并发重放只执行一次，并返回相同事件。
- 同一个 `clientOrderId` 被用于不同订单条件时，原订单不受影响。

## 5. 尚未解决的故障边界

- `appliedExecutions`、命令结果缓存、订单和订单簿都只在当前 JVM 内存中；进程重启后全部丢失，缓存也没有过期 / 容量策略。
- 两个 `OrderCommandProcessor` 实例各有独立锁和缓存，不能协调相同订单或请求。
- 订单簿变更、订单状态更新和事件缓存没有共同的持久化事务。如果中途抛错，不能声称自动回滚或 exactly-once。
- 当前 `OrderEntry` 没有映射该版本与 execution 去重历史；Space `write/change` 仍不是本阶段实现的乐观 CAS。
- 交易执行回报已经应用但进程在缓存响应前崩溃的情况，还需要 durable inbox / outbox 或等价事务日志来恢复。

因此，这一小步证明的是：**一个 JVM 内版本检查、对象内 execution 去重、处理器内命令重放和单点串行访问有明确行为**。下一步要选定持久状态来源，并让版本 / 去重记录与状态修改共享可靠提交边界，再测两个独立处理器之间的冲突。
