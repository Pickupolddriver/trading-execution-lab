# 学习路线图

本项目按阶段推进：先建立可验证的订单领域行为，再逐步引入分布式状态、故障处理和外部协议。路线图描述的是计划，阶段是否完成以代码和实验结果为准。

## 当前进度与下一步

- 阶段 1：已写基础领域模型，并补充 `clientOrderId`、`OrderType`、`limitPrice`、`TimeInForce.DAY`；编译与验证由项目使用者执行。
- 阶段 2：已写本地 Space、订单快照、读写演示和已有测试源码；尚未完成运行验证。见[Space 实验](space-lesson.zh-CN.md)。
- 阶段 4A 预备练习：单份行情快照的交易所模拟器已实现并通过 UT；它不是撮合引擎。
- 阶段 4A：单证券内存版 OrderBook 已实现并通过 UT，按价格优先 / 同价 FIFO 撮合，并返回买卖双方的 Trade 事实。见[OrderBook 设计说明](order-book-design.zh-CN.md)。
- 下一步：回到阶段 3，研究同一 symbol 的订单簿如何路由和串行处理，再测量访问成本、顺序和热点。当前 OrderBook 仍是单进程内存对象，不是分布式订单簿。不要把同 ID 覆盖写入当成完整幂等，也不要把单 JVM 实验当成集群一致性证明。
- 后续实现交接见[实现指导](implementation-guide.zh-CN.md)，可把其中一个任务直接交给 DeepSeek；每次只实现一个任务。

## 阶段 1：领域模型与订单状态

**概念：** 订单和成交生命周期、持仓更新、状态迁移合法性、领域不变量。

**实现：** `Order`、`Execution`、`Position`、`OrderStatus` 和 `Order.applyExecution(...)`。

订单输入先支持 MARKET / LIMIT 和 DAY。区分内部 `orderId`、客户身份 `clientId` 与请求编号 `clientOrderId`。限价单要求正数限价，市价单禁止限价。DAY 目前只表示订单条件，尚无交易日历或到期机制。

**需要回答：** 同一成交重复到达怎么办？较旧成交晚于新成交到达怎么办？两个线程同时更新同一订单怎么办？

**退出条件：** 有确定性的订单状态机，并用单元测试覆盖合法和非法迁移。

## 阶段 2：GigaSpaces Space

**概念：** Space、`write / read / take / change`、对象身份和路由。

**实现：** 先把订单状态写入本地 Space，再引入集群。

**退出条件：** 能通过 GigaSpaces 存储、查询和更新订单。

## 阶段 3：分区与数据亲和性

比较按 `orderId`、`clientId` 和 `symbol` 路由的策略，记录每种方案对访问成本、顺序和扩展性的影响。

先画出“订单查询、成交更新、账户风险检查、持仓更新”各自需要的数据，再部署至少两个分区做实验。记录是否跨分区、热点分布和实际延迟；当前 `orderId` 路由只是入门选择。PU 是部署与处理逻辑的单元，分区是数据分布的单元，写清二者关系。

**退出条件：** 形成有可测量取舍依据的分区决策。

**状态：** 尚未实现。当前本地 `OrderEntry` 按 `orderId` 路由只是阶段 2 的单 Space 示范；尚无多分区实验或性能数据。

## 阶段 4：事件处理

引入 `NewOrder`、`CancelOrder` 和 `ExecutionReport` 命令 / 事件，重点明确事件顺序和确定性处理。

拆成小任务：4A（预备练习，已完成）实现确定性的交易所模拟器，按 bid / ask、可用数量和限价生成成交；4B 接入新单处理与确认 / 拒绝；4C 接入成交回报和持仓；4D 处理撤单请求及确认、DAY 到期。先使用直接 Java 调用解释流程，再接 Space 事件容器。40/100 应来自可用数量，不再由演示入口随意制造。

**退出条件：** 行情不满足限价时不成交，可用量不足时部分成交，订单在确认后才进入可成交状态，撤单请求与撤单成功有明确区别。不要求这一阶段实现真实撮合簿。

## 阶段 5：并发与幂等

加入乐观版本控制、成交 ID、幂等检查和重复事件抑制，验证并发更新时不会重复计入成交或持仓。

**退出条件：** 同一成交重复投递、两个处理者并发写、旧快照覆盖新状态都有明确结果；去重信息与状态更新具有一致的提交边界。订单成交与持仓不能一边成功一边丢失。同 ID 写入、进程内 Set、FIX 会话序号都不能单独证明业务幂等。

## 阶段 6：高可用

运行主备实例并注入故障，观察主节点、备节点、请求在途状态和恢复行为。

**实验：** 终止主节点、终止备节点、重启节点、中断网络连接。

**退出条件：** 记录部署拓扑、复制方式、操作确认时点、故障后状态与重复处理结果。只对实际执行的故障实验下结论。

## 阶段 7：恢复与持久化

在理解内存状态行为后接入 PostgreSQL，并定义数据来源、持久化延迟容忍度和 Space 重建策略。

**退出条件：** 重启后恢复订单条件、状态、成交去重信息和持仓；说明异步持久化可能丢失的时间窗口。当前 `OrderEntry` 只是快照，不能据此恢复完整聚合。

## 阶段 8：迷你执行服务

集成执行网关、订单处理器、风控引擎、交易所模拟器和持仓状态，串通一笔订单的完整处理路径。

**退出条件：** 一笔新单可被接受或拒绝，成交更新订单与持仓，撤单只在确认后终结；展示一条成功链路和一条失败链路。

## 阶段 9：FIX

在领域模型稳定后接入 QuickFIX/J，处理以下消息及会话语义：

- `35=D`：NewOrderSingle（新订单）
- `35=8`：ExecutionReport（执行回报）
- `35=F`：OrderCancelRequest（撤单请求）
- 序列号、重发和重复消息

先约定 FIX 4.4 与模拟对手方的字段规范，再写 QuickFIX/J 适配。映射 `ClOrdID(11)`、`OrdType(40)`、`Price(44)`、`TimeInForce(59)`，区分客户请求编号和交易场所 `OrderID(37)`。订单的新单时间与后续请求时间不能混用。先支持新单与执行回报，再支持撤单；改单 `35=G` 留作独立扩展。

**退出条件：** 两个本地 FIX 会话完成新单、部分成交、全部成交及撤单；断线重连 / 重发不重复计入成交。终态的 `LeavesQty` 单独映射，不能直接使用 `quantity - filledQuantity`。字段必填规则以选定 FIX 版本和对手方规范为准。

## 阶段 10：面试与系统设计

练习解释内存状态、分区、故障切换、重复抑制、顺序保证、网络分区行为，以及本架构与常规 Spring 微服务的差异。
